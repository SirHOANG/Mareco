# Mareco — Mobile Operation Recorder

I want to build a **new-generation mobile macro/operation recorder app** called **Mareco**.

The development environment is **Windows**, but the final application is intended to run on **Android mobile devices**.

Mareco is inspired by the **Operation Recorder / Macro Recorder** features found in Android emulators such as **LDPlayer, MuMu Player, and BlueStacks**. Instead of requiring users to install a separate autoclicker app from the Play Store, Mareco should provide a more complete operation-recording experience in one application.

The main purpose is to record a user's physical interactions with the device—such as taps, clicks, swipes, and supported key presses—and replay those actions automatically.

The goal is to make Mareco useful for repetitive tasks where the user wants to automate the same sequence of actions repeatedly.

## Core Concept

Mareco should work like this:

**Record → Stop → Configure → Execute**

Example:

1. Open Mareco.
2. Press **Start Recording**.
3. Perform actions normally on the phone.
4. Mareco records the user's supported touch/input actions.
5. Press **Stop Recording**.
6. Open the **Settings / Gear** button.
7. Configure execution settings.
8. Press **Run**.
9. Mareco replays the recorded sequence automatically.

---

# Core Features

## 1. Input Recording

Mareco should record supported user interactions in real time.

The recorder should be able to capture:

* Tap
* Long press
* Swipe
* Drag
* Touch coordinates
* Touch duration
* Delay between actions
* Multiple consecutive touches
* Supported physical key presses
* Action order

Each action should be stored as a structured event rather than simply recording the screen.

For example:

```text
Tap X: 500 Y: 800
Wait: 500 ms
Swipe X1: 300 Y1: 700 → X2: 700 Y2: 700
Wait: 1000 ms
Tap X: 900 Y: 150
```

The recorder should preserve the original timing between actions whenever possible.

---

# 2. Recording Controls

The main interface should have a simple and beginner-friendly control panel.

Required buttons:

### Start Recording

Begins recording supported user input.

### Stop Recording

Stops the current recording and saves it as a macro.

### Settings / Gear

Opens the configuration screen after a recording has been created.

### Run / Execute

Starts replaying the recorded macro.

### Pause

Temporarily pauses macro execution.

### Stop Execution

Immediately stops the currently running macro.

The UI should clearly show whether Mareco is currently:

```text
IDLE
RECORDING
READY
RUNNING
PAUSED
STOPPED
```

---

# 3. Macro Timeline / Editor

After recording, show the recorded actions in a timeline.

Example:

```text
Macro: Farming Loop

01  Tap       (500, 800)
02  Wait      500 ms
03  Swipe     (300,700) → (700,700)
04  Wait      1.0 sec
05  Tap       (900,150)
06  Wait      2.0 sec
```

Users should be able to:

* View recorded actions
* Delete an action
* Edit an action
* Change delays
* Change coordinates when supported
* Reorder actions
* Add a delay
* Duplicate an action
* Clear the entire recording

This would make Mareco much more powerful than a basic autoclicker.

---

# 4. Execution Settings

After finishing a recording, the user should be able to configure how the macro executes.

Create an **Execution Settings** screen.

## Stop Condition

Provide two modes:

### Execution Count / Time

Allow the user to specify how many times the macro should execute.

Example:

```text
Executions: 10
```

or, if implementing time-based execution:

```text
Run for: 30 minutes
```

### Infinite

The macro continues running indefinitely until the user manually presses **Stop**.

---

# 5. Execution Speed

Add an **Execution Speed** setting.

This controls how quickly recorded actions are replayed.

Example:

```text
Execution Speed

0.5x
1.0x   ← Default
1.5x
2.0x
5.0x
10x
```

At **1.0x**, Mareco should attempt to reproduce the original timing.

At higher speeds, delays between actions can be reduced.

The app should prevent unsafe or impossible timing values that the Android input system cannot reliably execute.

---

# 6. Simulate Execution

Add:

**Simulate Execution**

Description:

> Mimics the original recorded click and touch behavior as closely as possible.

This should be **enabled by default**.

The goal is to make replayed actions behave as naturally as possible instead of simply firing actions as quickly as the system allows.

---

Allow users to save multiple macros.

Example:

```text
My Macros

├── Farming
├── Daily Quest
├── Login Routine
├── Resource Collection
└── Test Macro
```

Each macro should have:

* Name
* Description
* Creation date
* Last modified date
* Number of actions
* Execution settings

Users should be able to:

* Create
* Rename
* Duplicate
* Delete
* Export
* Import

macros.

# 8. Macro Import / Export

Create a simple macro file format.

For example:

```text
.mareco
```

The format should contain:

* Device/display information
* Recorded actions
* Coordinates
* Timing information
* Execution settings
* Macro metadata

Example structure:

```json
{
  "name": "Farming Macro",
  "version": 1,
  "actions": [
    {
      "type": "tap",
      "x": 500,
      "y": 800,
      "delay": 500
    }
  ],
  "execution": {
    "mode": "infinite",
    "speed": 1.0,
    "simulate": true
  }
}
```

# 9. Device / Screen Compatibility

Because Android devices have different resolutions and aspect ratios, Mareco should consider coordinate scaling.

For example:

```text
Recorded on:
1080 × 2400

Current device:
720 × 1600
```

Mareco should optionally scale coordinates proportionally.

Provide a setting such as:

**Coordinate Scaling**

* Original coordinates
* Scale to current screen
* Preserve aspect ratio

Also warn users when the current screen resolution is significantly different from the recording device.

---

# 10. Delay Configuration

Allow users to configure delays between actions.

For example:

```text
Action Delay

Original
500 ms

Custom:
1000 ms
```

Add optional:

**Randomized Delay**

This can slightly vary delays around the configured value.

Example:

```text
Base delay: 1000 ms
Random range: ±200 ms
```

This should be optional and disabled by default.

---

# 11. Safety Features

Mareco should always provide an easy way to stop automation.

Add:

### Emergency Stop

A clearly accessible **STOP** control should immediately terminate macro execution.

Also consider:

* Stop when the app loses permission
* Stop when the screen turns off
* Optional maximum execution time
* Optional maximum execution count
* Confirmation before starting an infinite macro
* Prevent accidental execution from the settings screen

The user should always be able to regain control of the device.

---

# 12. Permission Setup

If Android requires accessibility or other system permissions for input automation, Mareco should provide a beginner-friendly setup screen.

Example:

```text
Mareco Setup

✓ Application installed

⚠ Accessibility permission required

[Open Android Settings]

After enabling the permission:

[Check Permission Again]
```

Do not silently request or bypass Android security restrictions.

Explain clearly what each permission is used for.

The overlay should avoid interfering with the application being recorded.

The overlay should be minimal and unobtrusive.

# 16. Suggested Advanced Features

If practical, consider adding these features in later versions:

### Macro Editor

Visually edit the recorded timeline.

### Loop Delay

Add a configurable delay between complete macro loops.


### Action Groups

Allow users to group actions together.


If technically possible within Android's permitted APIs, support simple conditions such as:

### Macro Statistics

Provide presets such as:

```text

```

### Dark Mode

Support both:

* Light mode
* Dark mode

### Haptic Feedback

Give subtle vibration feedback when:

* Recording starts
* Recording stops
* Macro starts
* Macro stops

# 17. Important Android Limitations

Before implementing the system, investigate which Android APIs are officially available for:

* Touch automation
* AccessibilityService
* Gesture dispatch
* Floating overlays
* Physical key events
* Background execution
* Screen resolution detection
* Permission handling

Do NOT assume that Android allows unrestricted global input injection.

The implementation should use legitimate Android APIs and clearly explain limitations where necessary.

If a feature cannot be implemented reliably on standard Android without root, ADB, or emulator-specific privileges, clearly separate it as an optional advanced feature rather than pretending it works universally.

---

# 18. Development Requirements

I am developing the project on **Windows**.

Make the development setup straightforward and suitable for a developer using a Windows PC.

Prefer a lightweight architecture because the development machine has limited RAM.

Avoid unnecessary heavyweight dependencies.

Before writing a large amount of code:

1. Design the architecture.
2. Identify Android API limitations.
3. Create the basic UI.
4. Implement recording.
5. Implement replay.
6. Implement execution settings.
7. Implement macro storage.
8. Add the editor.
9. Add advanced features afterward.

Build the project incrementally so each stage can be tested on a real Android device.

---

# Product Goal

Mareco should feel like a **mobile-native version of an emulator Operation Recorder**, rather than a basic Play Store autoclicker.

The core experience should be:

**Record your actions → configure the macro → replay them automatically.**

The application should be:

* Free
* Simple
* Lightweight
* Beginner-friendly
* Reliable
* Transparent about Android permissions
* Easy to configure
* More flexible than a basic autoclicker

The primary focus should be **macro recording and replay**, with advanced automation features added only when they are technically reliable and supported by Android.
